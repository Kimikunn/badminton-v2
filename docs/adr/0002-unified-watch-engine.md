# 触发层合并为单一监控引擎与取数计划

系统原有 `venueWatchPoller`（定时轮询 + 快照 diff）与 `venueLockRush`（每天 09:00 抢新放票日）两套相互独立的触发机制，二者下游逻辑（拉数据 → 匹配 → 锁场 → 通知）本质相同却各自实现，还产生了循环依赖。分析后确认两者唯一区别是**何时拉、拉哪天**：rush 针对时刻已知的新放票日（09:00 赛跑，需秒级突发重试），轮询针对时刻未知的回流场次（退订、未支付超时）。我们决定将触发层重构为**一个监控引擎 + 一张取数计划表**：窗口内每个日期有独立拉取节奏，新放票日 09:00 进入突发模式（1s × N 直至数据出现）随后并入常规节奏，下游共用同一条"匹配意图 → 锁场 → 通知"管道。

## Considered Options

- **废弃 rush，全靠高频轮询**：轮询间隔受对方接口压力限制无法秒级，9 点抢新是赛跑，慢几秒就可能输，否决。
- **保持两套独立实现**：重复逻辑与循环依赖已经造成实际维护问题（`dateStr` 复制 4 份、lazy require 绕循环依赖），否决。

## Consequences

- 快照 diff 只服务于"通知不重复"，锁场去重由锁场记录独立负责，两者解耦。
- 取数计划成为引擎的显式内部结构，未来调整节奏（如赛前 1 小时加密轮询）只改计划，不动管道。
