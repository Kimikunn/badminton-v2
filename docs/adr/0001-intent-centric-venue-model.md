# 以订场意图为中心重构监控锁场系统

系统的旧模型以"监控目标（venue_watch_target）"为中心，自动锁场只是目标上的一个附属开关；实际使用者的心智是"我声明想订什么场（哪天有空、打几小时、偏好哪个场），系统自动帮我盯和抢"。我们决定将领域模型重构为以**订场意图（Booking Intent）**为唯一中心概念：监控与锁场降级为意图的执行手段，用户界面上不再出现；数据库表（`venue_watch_*` → 意图语言命名）与 API 一并重命名，v1 废弃列（凭证类、`area_id/area_name` 等）随迁移删除。

## Considered Options

- **只重构代码不动表**：表名与代码语言长期不一致，新读者会持续困惑，否决。
- **监控与锁场拆成两个独立功能**：与真实使用流程不符——用户从不想要"只监控"，监控永远是订场意图的手段，否决。

## Consequences

- 旧模型中"目标选具体时段格子"被"时间窗口 + 连续时长"取代（用户表达"17-20 点之间打 2 小时"，而非逐个勾格子）；连续小时允许跨场地。
- 意图是长期有效的站位指令，没有"完成后自动结束"的生命周期状态；单次日期意图过期自然失效。
