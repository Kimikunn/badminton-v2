# PRD: 监控锁场系统重构为订场意图模型

## 背景

现有"订场监控 + 自动锁场"功能逻辑混乱：领域模型以"监控目标"为中心而非用户的真实意图；触发层有轮询与 9 点抢新两套独立机制，下游逻辑重复且存在循环依赖；数据库残留 v1 废弃列；前端面板把"配置监控规则"直接暴露给用户，且锁场记录、通知历史等已有后端能力在 UI 完全不可见。

领域语言与决策已固化于根目录 `CONTEXT.md` 及 `docs/adr/0001`、`docs/adr/0002`。

## 需求

### 领域模型（R1）

以**订场意图**为唯一中心概念，取代"监控目标"。一个意图包含：

- **时间表达**：单次日期 或 每周几（可多选），二选一
- **时间窗口**：如 17:00-20:00，表示"这个范围内我有空"
- **打球时长**：N 小时；满足条件 = 窗口内找到**连续 N 个**小时时段并锁到，连续小时**允许跨场地**，不接受断开
- **同时片数**：同一小时需要几片场（1-3，默认 1）
- **场地偏好**：有序场地列表；为空时用全局场地优先级
- **模式**：自动锁场 / 仅提醒，默认自动锁场
- **开关**：启用 / 停用

### 生命周期（R2）

- 意图是长期有效的站位指令：启用期间每逢设定时间就监控并锁场，**没有"完成后自动结束"**；不想要了就关闭或删除
- 每周意图的每次发生相互独立：当次锁到即停手，下周自动滚动
- 单次日期意图在日期过后自然过期（不删数据，UI 标记）
- 放票窗口为今天起 4 天，同一时刻最多 4 个意图处于可订窗口内

### 锁场与重试（R3）

- **抢失败不放弃**：锁场被他人抢先，格子再次可订时再抢，直到该时段过去
- **两击降级**：锁场成功但 5 分钟内未支付导致订单取消后，同一时段再空出时自动重锁一次并再次通知；同一时段连续两次超时未支付，该次意图降级为仅提醒并告知原因
- 锁场去重只针对"已锁到"的记录；失败的尝试不得阻塞后续重试

### 触发层（R4）

- 轮询与 9 点抢新合并为**单一监控引擎 + 取数计划**（ADR-0002）：新放票日 09:00 突发模式（1s 间隔重试直至数据出现，有上限），之后并入常规轮询节奏；下游共用同一条"匹配意图 → 锁场 → 通知"管道
- 快照 diff 只用于通知去重；锁场去重独立

### 前端（R5）

- 订场页内重做面板为**意图卡片列表**：每张卡显示意图内容（每周几/哪天、窗口、时长、片数、场地偏好、模式）+ 实时状态（监控中 / 已锁到待支付 / 已过期 / 已降级）
- 卡片可展开查看最近的锁场记录与通知历史（现有后端能力接入 UI）
- 创建流程只问三件事：**哪天有空、打几小时、偏好哪个场**；时段格子选择从主流程移除
- 全局场地优先级与总开关保留

### 后端（R6）

- 数据表重命名为意图语言（`venue_watch_*` → 新命名），v1 废弃列（`token_user`、`webhook_*`、`poll_interval_sec`、`venue_watch_targets.area_id/area_name`）随迁移删除
- API 路径改为意图语言命名；前端同步切换
- 消除重复实现：`dateStr` 等复制粘贴的 helper 归一；poller/digest 循环依赖解除；validators 与 controller 的双重校验合并为一层

## 非目标

- 不改变外部体育馆 API 的调用方式（签名、下单链路、`listAreaLease` 等保持现状）
- 不改变推送通道的种类与配置方式（仍在 server `.env`）
- 不做支付状态回查（外部系统不支持；未支付超时通过"格子回流可订"间接检测）
- 不动每日摘要（digest）的内部逻辑

## 验收标准

1. 旧 `venue_watch_*` 数据无损迁移到新表，废弃列不再存在于 schema
2. 创建"每周一、窗口 19:00-21:00、时长 2 小时、1 片场、自动锁场"的意图后，系统在窗口内锁到连续 2 小时后该次停手；下周一自动重新生效
3. 锁场失败的时段，格子回流可订后能自动重抢
4. 同一时段两次超时未支付后降级为仅提醒，并推送原因
5. 09:00 新放票日突发拉取与常规轮询由同一引擎驱动，下游管道只有一份实现
6. 前端订场页展示意图卡片列表，创建流程不含时段格子选择；卡片可见锁场记录与通知历史
7. `server/test/` 相关测试全部更新并通过；无残留对旧表名/旧 API 路径的引用
